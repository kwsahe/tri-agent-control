# 실사용 기록 — 회의실 예약 시스템

TriAgent Control로 실제 풀스택 프로젝트(`meeting-room-booking`: FastAPI + SQLite, React + Vite)를 기능 단위로 만들면서 생긴 문제와 수정을 적는다. 큰 구현은 TriAgent의 Claude Code(구현 담당)가 맡고, 사람(운영자)은 계획 승인·결과 확인·TriAgent 수정을 맡는다.

## 준비 (2026-11-01)

- 운영자가 만든 것: 폴더, git, `.venv`(fastapi·uvicorn·pytest·httpx), Vite React 템플릿 + Vitest, `/api/health` 하나와 테스트 하나, 최상위 `package.json`의 `test`(화면 Vitest + 서버 pytest)·`build` 스크립트.
- 최상위 스크립트를 둔 이유: TriAgent 자동 검증은 작업 폴더 최상위의 `package.json`과 `tests/`만 찾는다. `backend/`·`frontend/`로 나눈 프로젝트는 최상위 스크립트가 없으면 "자동 검증 없음"이 된다.

## 문제 기록

### 1. 세션 worktree에서 화면 테스트·빌드가 항상 실패 (수정함)

- **증상**: 모델을 부르기 전 점검에서, 세션 worktree의 `npm test`·`npm run build`가 `'vitest'은(는) 내부 또는 외부 명령... 아닙니다`로 실패.
- **원인**: worktree에는 Git이 추적하지 않는 의존성 폴더가 없어서 사용자 폴더의 것을 연결하는데, 최상위(`.venv`, `node_modules`)만 연결했다. 이 프로젝트의 `node_modules`는 `frontend/` 아래에 있다.
- **영향**: 모노레포 구성에서는 자동 검증이 매번 실패해, 파이프라인이 통과할 수 없었다.
- **수정**: `triagent/domain/gitops.py` — 한 단계 아래의 의존성 폴더(`frontend/node_modules`, `backend/.venv` 등)도 연결하고, 정리할 때도 그 연결만 끊는다. 회귀 테스트 추가.
- **확인**: 같은 점검을 다시 돌려 worktree에서 `npm test`(화면 1 + 서버 1)·`npm run build` 통과, 원본 `frontend/node_modules`와 사용자 브랜치·파일은 그대로.

### 2. 기능을 이어서 만들 때 이전 기능이 다음 세션에 없음 (운영 방식으로 해결)

- **증상(예상)**: 세션마다 사용자 폴더의 마지막 커밋에서 worktree를 만든다. 기능 1의 결과는 `triagent/<세션ID>` 브랜치에만 있으므로, 기능 2 세션은 기능 1 없이 시작한다.
- **운영 방식**: 기능 하나가 끝나면 운영자가 결과를 확인하고 세션 브랜치를 `main`에 병합(fast-forward)한 뒤 다음 기능을 시작한다.
- **개선 후보**: 대시보드에 "결과를 내 브랜치에 반영" 단추 (테스트 통과·충돌 없음일 때만).

## 기능 기록

### 기능 1 — 회의실·예약 API (완료, 2사이클)

- 요청 748자 (예전 500자 잘림 버그였다면 뒷부분 "이번에 하지 않는 것"이 잘렸을 길이). 계획이 요청 전체를 반영했다.
- 사이클 1: Claude가 `db.py`·`main.py` 구현(54초) → Antigravity가 임시 DB fixture와 테스트 16개 추가(114초) → 자동 검증 통과 → Codex가 "복합 필터·자정 경계 테스트 누락" 지적.
- 사이클 2: Claude는 코드 결함이 아니라며 변경 없음(26초) → Antigravity가 테스트 2개 추가 → Codex "지적 없음".
- 결과: 커밋 2개(`a914668`, `0131d79`), 서버 테스트 19개. 운영자가 `main`에 fast-forward 병합 후 `npm test` 통과, 테스트가 실제 `booking.db`를 만들지 않음을 확인.
- 관찰:
  - **검토가 테스트 누락만 지적해도 구현 턴이 먼저 돈다.** 사이클 2의 Claude 턴은 "변경 없음"으로 26초를 썼다. 개선 후보: 지적이 테스트 파일에만 해당하면 그 사이클의 구현 단계를 건너뛴다.
  - Codex 검토 답변이 "…점검하겠습니다." 같은 서론으로 시작한다 (형식은 "고칠 점 한 줄씩"). 판정에는 영향 없음.

### 기능 2 — 겹침 검사·예약 변경·빈 시간 조회 (완료, 1사이클)

- 요청 812자. 계획이 맞닿은 시간 허용, `BEGIN IMMEDIATE` 동시성, PATCH 자기 제외, 운영 시간 자르기를 모두 반영.
- 사이클 1: Claude 구현(73초) → Antigravity 테스트 19개 추가(162초, 총 38개) → 자동 검증 통과 → Codex "지적 없음".
- 운영자 독립 확인 (테스트와 별개 스크립트): 10:00 종료/10:00 시작 허용, 겹침 409, 다른 회의실 허용, PATCH 자기 제외, PATCH로 겹치게 하면 409, 빈 시간이 09:00~18:00로 잘림, date 없으면 422 — 모두 요청대로.
- `main` 병합 후 `npm test` 통과 (화면 1, 서버 38).
- 관찰: Starlette가 `httpx` 대신 `httpx2`를 쓰라는 경고를 낸다 (테스트 결과에는 영향 없음, 프로젝트 의존성 정리 거리).

### 기능 3 — 주간 달력 화면 (1차 실행 중단 → 수정 후 재실행)

#### 3. 구현 턴 하나 만에 "최대 토큰 200,000 도달"로 세션 종료 (수정함)

- **증상**: 화면 구현 턴(132초, 비용 $0.53) 직후 세션이 끝났다. 테스트·검토를 한 번도 거치지 않았고 커밋도 0개.
- **원인**: 그 턴의 실측 사용량 24만 3천 개 중 20만 2천 개(83%)가 캐시 읽기였다. 캐시 읽기는 도구를 부를 때마다 같은 문맥을 다시 읽은 양이라, 작업량이 아니라 도구 호출 수에 비례한다. 코딩 한도가 이것까지 세서, 파일을 여러 개 만드는 큰 작업은 한 턴 만에 한도를 넘었다.
- **수정**: 한도 판정에만 "처리 토큰"(캐시 읽기 제외: Claude의 `cache_read_input_tokens`, Codex의 `cached_input_tokens`)을 쓴다. 화면의 실측 토큰 표시는 그대로. 회귀 테스트: 같은 사용량(실측 283,544 / 처리 41,779)이면 한도에 걸리지 않음.

#### 4. 빌드 결과물이 에이전트 변경으로 잡힘 (수정함)

- **증상**: Claude가 검증하려고 `npm run build`를 돌려 생긴 `frontend/dist/`(6개 경로)가 변경 파일로 잡혔다.
- **영향**: 변경 파일 한도(50개)를 채우고, 사이클 커밋 때 `git add`가 "ignored" 오류(exit 1)로 실패한다 (임시 저장소에서 재현).
- **수정**: 변경 감지 직후 `git check-ignore`로 `.gitignore`에 걸리는 경로를 뺀다 (이미 추적 중인 파일은 그대로 변경으로 본다). 역할 범위 검사·diff·커밋 모두 이 목록을 쓴다.

- **1차 실행 처리**: 세션은 끝났고 worktree의 구현은 커밋되지 않았다. 검증·검토를 거치지 않은 결과라 버리고, 수정한 TriAgent로 기능 3을 처음부터 다시 실행한다.
